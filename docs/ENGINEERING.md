# Engineering decisions and limits

- **Database is the source of truth.** Redis Pub/Sub distributes ephemeral tracking/status events across instances. Reservations use PostgreSQL transactions rather than a Redis lock with lease-expiry races. Redis persistence is unnecessary for these ephemeral messages.
- **No transactional outbox yet.** A process may die between commit and publication. Redis downtime may lose events. WebSocket reconnect + periodic snapshot polling recovers current state, but cannot replay every event. Add an outbox and durable stream for an audit-grade feed.
- **Dispatch is a greedy per-order heuristic.** It scans the available fleet and uses a heap to try alternative candidates under contention. It does not globally optimize multiple simultaneous orders, account for traffic, driver shifts, capacity, or fairness. Fixed speed and static prep estimates are intentionally simple. Nearest-driver is cheaper and selects shorter pickup routes; timing alignment can select a farther driver.
- **Simulation is browser-controlled.** Every 1.5 seconds while enabled, a request moves accepted drivers 18% of the remaining straight-line distance. The destination switches after pickup. Movement does not automatically change order states. The map is a schematic coordinate projection, not a road-routing map. Multiple active simulators make movement faster; a single scheduled simulation worker would improve consistency.
- **Authorization is deliberately out of scope for this demo.** Roles change UI controls only. There are no user accounts, row-level ownership checks, rate limits, payments, or sensitive customer addresses. Public deployment requires authentication, driver ownership checks, TLS, secrets management, request limits, and an operations review.
- **Schema constraints protect concurrency invariants.** Active order and driver indexes enforce uniqueness. Application code enforces the directed state graph and accepted-assignment requirement. A database administrator can still bypass application state rules. Tests use isolated databases and are destructive only within that chosen test database.
- **Scaling boundaries.** Dashboard reads are unpaginated; the full fleet scan is O(n). Synchronous ORM work is acceptable for this bounded demo; dispatch runs in a thread pool. Adopt pagination, an async ORM or consistent sync route execution, spatial candidate filtering, and PostGIS as workloads grow. No multi-region or high-availability guarantees are claimed.
- **Driver lifecycle.** Dispatch reserves a driver before acceptance, and only completion/cancellation releases it. There is no rejection/timeout/reassignment mechanism. Those are valuable next features alongside assignment history and idempotency keys for order creation.
- **Deployment.** Compose provides health-gated startup, persistent PostgreSQL, and Nginx WebSocket forwarding. It is local deployment infrastructure, not a hardened public production service. Redis is coordination/fanout, not a demonstrated response cache. Add query caching only after measuring an actual need.
- **Metrics.** JSON request logs include duration and request IDs. Benchmarks measure pure ranking latency and a self-defined timing score, not end-to-end HTTP throughput, database contention, delivery success rate, or real-world ETA accuracy.
